# API Reference

Endpoint reference for the GLiNER2 inference service running on `jarvita-agx`.

- **Base URL (LAN):** `http://192.168.1.177:8013`
- **Container port:** `8012` (published on host port `8013`)
- **Content type:** all `POST` endpoints take and return `application/json`

Every example below is copy-pasteable. Request/response pairs marked *verified*
were captured from the live service on `jarvita-agx`.

Interactive docs, generated by FastAPI, are served from the same base URL:

| Path | What it is |
|---|---|
| `/docs` | Swagger UI |
| `/redoc` | ReDoc |
| `/openapi.json` | Raw OpenAPI schema |

```bash
curl -s http://192.168.1.177:8013/openapi.json | head -c 400
```

## Endpoint summary

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness plus model/device state |
| GET | `/version` | Installed `gliner2` package version |
| POST | `/extract_entities` | Zero-shot named entity extraction |
| POST | `/classify_text` | Text classification |
| POST | `/extract_structured` | Structured JSON extraction against a schema |
| POST | `/extract_multitask` | Entities + classification + structure in one pass |

## GET /health

No parameters. Returns the configured model, whether it is resident in memory,
and the device it landed on.

```bash
curl -s http://192.168.1.177:8013/health
```

Verified response (`fastino/gliner2.5-base-v1`, model loaded, GPU):

```json
{
  "status": "ok",
  "model_id": "fastino/gliner2.5-base-v1",
  "model_path": "./models/fastino/gliner2.5-base-v1",
  "architecture": "boundary",
  "model_class": "BoundaryExtractor",
  "loaded": true,
  "device": "cuda",
  "gpu": "Orin",
  "max_concurrent_inferences": 1
}
```

Builds that include GLiNER2.5 dispatch also return `architecture` and
`model_class`:

```json
{
  "status": "ok",
  "model_id": "fastino/gliner2.5-multi-v1",
  "model_path": "./models/fastino/gliner2.5-multi-v1",
  "loaded": true,
  "architecture": "boundary",
  "model_class": "AutoExtractor",
  "device": "cuda",
  "gpu": "Orin",
  "max_concurrent_inferences": 1
}
```

Field notes:

| Field | Meaning |
|---|---|
| `status` | Always `"ok"` if the process is up — this is a liveness check, not a model readiness check |
| `loaded` | `false` until the model is resident. With `MODEL_PRELOAD=0` this stays `false` until the first inference request |
| `device` | `"cuda"` or `"cpu"`. `"cpu"` on a Jetson means the GPU was not visible — see the runbook |
| `gpu` | `torch.cuda.get_device_name(0)`; `"Orin"` on an AGX Orin. `null` on CPU |
| `architecture` | `"span"` for GLiNER2, `"boundary"` for GLiNER2.5. `null` before load |
| `model_class` | `GLiNER2` or `AutoExtractor`. `null` before load |
| `max_concurrent_inferences` | Current semaphore width |

`/health` never touches the GPU, so it stays responsive while an inference is in
flight. Use it as a container healthcheck; use a real inference request if you
need to prove the model works.

## GET /version

```bash
curl -s http://192.168.1.177:8013/version
```

Response shape:

```json
{ "gliner2": "2.0.0" }
```

The value is whatever `gliner2.__version__` reports for the pin baked into the
image, or `"unknown"` if the package does not expose `__version__`. Check this
first when behavior differs between two containers.

## POST /extract_entities

Zero-shot NER. You supply the label set per request; nothing is fine-tuned.

Request body:

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` (default 20000) |
| `labels` | array of strings, **or** object mapping label → description | yes | Non-empty, `<= MAX_LABELS` (default 256) |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Patient received 400mg ibuprofen for severe headache at 2 PM.",
    "labels": ["medication", "dosage", "symptom", "time"]
  }'
```

Verified response:

```json
{
  "entities": {
    "medication": ["ibuprofen"],
    "dosage": ["400mg"],
    "symptom": ["headache"],
    "time": ["2 PM"]
  }
}
```

The response keys are exactly the labels you sent. A label with no match maps to
an empty list. Values are the surface spans as they appear in `text`.

Labels can also be an object, where the value is a natural-language description
used to disambiguate the label:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Patient received 400mg ibuprofen for severe headache at 2 PM.",
    "labels": {
      "medication": "name of a drug administered to the patient",
      "dosage": "amount and unit of the drug"
    }
  }'
```

## POST /classify_text

Request body:

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `labels` | array of strings, **or** object mapping task name → array of class labels | yes | Non-empty, `<= MAX_LABELS` entries |

The object form names the classification task, and the response is keyed by that
name. This is the form to prefer, because the output key is then predictable.

```bash
curl -s -X POST http://192.168.1.177:8013/classify_text \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The battery life is terrible and it overheats constantly.",
    "labels": {"sentiment": ["positive", "negative", "neutral"]}
  }'
```

Verified response:

```json
{ "sentiment": "negative" }
```

Multiple independent classification tasks can be requested in one call by adding
more keys to the `labels` object:

```bash
curl -s -X POST http://192.168.1.177:8013/classify_text \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The battery life is terrible and it overheats constantly.",
    "labels": {
      "sentiment": ["positive", "negative", "neutral"],
      "topic": ["battery", "display", "software", "build quality"]
    }
  }'
```

## POST /extract_structured

Fills a declared schema from free text. Backed by `extract_json()` in the
library.

Request body:

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `schema` | object | yes | Non-empty, `<= MAX_SCHEMA_FIELDS` top-level keys |

Each top-level key of `schema` is a record name; its value is a list of field
specs. A field spec is a `::`-delimited string:

```
"<field_name>::<dtype>"
"<field_name>::<dtype>::<description>"
```

`dtype` is `str` or `list`. The optional third segment is a natural-language
description that steers extraction.

```bash
curl -s -X POST http://192.168.1.177:8013/extract_structured \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The Sony WH-1000XM5 headphones cost $399 and ship in 3 days.",
    "schema": {
      "product": ["name::str", "price::str", "shipping::str"]
    }
  }'
```

Verified response:

```json
{
  "product": [
    {
      "name": "Sony WH-1000XM5 headphones",
      "price": "$399",
      "shipping": "3 days"
    }
  ]
}
```

Note the value is a **list** of records — the schema may match more than once in
a document. Index `[0]` only when you know the text holds a single record.

With descriptions:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_structured \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Goldman Sachs processed a $2.5M equity trade for Tesla Inc.",
    "schema": {
      "transaction": [
        "broker::str::Financial institution",
        "amount::str::Transaction amount",
        "security::str::Stock name"
      ]
    }
  }'
```

## POST /extract_multitask

Runs entity extraction, classification, and structured extraction against one
text in a single forward pass.

**Everything nests under `schema_config`.** There are no top-level `entities` /
`classification` / `structure` keys. Sending them at the top level is the most
common mistake with this endpoint and returns `400`.

Request body:

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `schema_config` | object | yes | Non-empty. All three sub-keys below are optional, but supply at least one |
| `schema_config.entities` | array of strings | no | Entity labels, `<= MAX_LABELS` |
| `schema_config.classification` | object | no | `{"name": str, "labels": [str, ...]}`, `labels` `<= MAX_LABELS` |
| `schema_config.structure` | object | no | `{"name": str, "fields": [...]}`, `fields` `<= MAX_SCHEMA_FIELDS` |

Each entry of `structure.fields` is an object:

| Key | Type | Default | Notes |
|---|---|---|---|
| `name` | string | — | Field name |
| `dtype` | string | `"str"` | `"str"` or `"list"` |
| `description` | string | `null` | Optional steering text |
| `choices` | array | `null` | Optional closed vocabulary for the field |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_multitask \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Apple CEO Tim Cook announced record revenue in Cupertino.",
    "schema_config": {
      "entities": ["company", "person", "location"],
      "classification": {"name": "sentiment", "labels": ["positive", "negative"]},
      "structure": {
        "name": "announcement",
        "fields": [
          {"name": "who", "dtype": "str"},
          {"name": "what", "dtype": "str"}
        ]
      }
    }
  }'
```

Verified response:

```json
{
  "announcement": [{"who": "Tim Cook", "what": "record revenue"}],
  "entities": {
    "company": ["Apple"],
    "person": ["Tim Cook"],
    "location": ["Cupertino"]
  },
  "sentiment": "positive"
}
```

The response is a flat object. Entities land under `entities`; the
classification lands under the `name` you gave it (`sentiment`); the structure
lands under its `name` (`announcement`) as a list of records. Key ordering is
not guaranteed — address the response by key.

## POST /extract_relations

Extract typed relation triples. **Requires a GLiNER2.5 boundary checkpoint** —
on a span model this returns `501`.

```bash
curl -X POST http://192.168.1.177:8013/extract_relations \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Satya Nadella, CEO of Microsoft, met Sam Altman of OpenAI in Seattle.",
    "relations": ["works_for", "met_with", "located_in"]
  }'
```

```json
{
  "relation_extraction": {
    "works_for": [["Satya Nadella", "Microsoft"]],
    "met_with": [["Satya Nadella", "Sam Altman"]],
    "located_in": [["Sam Altman", "Seattle"], ["OpenAI", "Seattle"]]
  }
}
```

Each relation name maps to a list of `[head, tail]` pairs. The model extracts
what the sentence supports and does not apply type constraints you did not give
it — above, `located_in` returned both a person and an organization.

| Field | Type | Notes |
|---|---|---|
| `text` | string | Subject to `MAX_TEXT_CHARS` |
| `relations` | list of strings | Relation type names; subject to `MAX_LABELS` |

On a span checkpoint:

```json
{"detail": "'extract_relations' requires a GLiNER2.5 boundary checkpoint; loaded model 'fastino/gliner2-large-v1' has architecture 'span'. Set MODEL_ID to e.g. fastino/gliner2.5-multi-v1."}
```

## POST /extract_entities_batch

Entity extraction over many documents in one call. Measured **4.2x faster per
document** than sequential single calls (24.0 ms/doc vs 100.4 ms/doc over 16
documents). **Requires a boundary checkpoint.**

```bash
curl -X POST http://192.168.1.177:8013/extract_entities_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": [
      "Apple CEO Tim Cook announced iPhone 15 in Cupertino.",
      "Satya Nadella leads Microsoft from Redmond."
    ],
    "labels": ["company", "person", "location"]
  }'
```

```json
{
  "results": [
    {"entities": {"company": ["Apple"], "person": ["Tim Cook"], "location": ["Cupertino"]}},
    {"entities": {"company": ["Microsoft"], "person": ["Satya Nadella"], "location": ["Redmond"]}}
  ]
}
```

`results` is positionally aligned with the `texts` you sent.

| Field | Type | Notes |
|---|---|---|
| `texts` | list of strings | Capped by `MAX_BATCH_SIZE` (default 64); each element subject to `MAX_TEXT_CHARS` |
| `labels` | list or object | Same shape as `/extract_entities`; applied to every document |

The whole batch occupies **one** inference slot, so it does not contend with the
`MAX_CONCURRENT_INFERENCES` semaphore per document. Prefer this over raising
concurrency for bulk work.

## Errors

The service returns standard HTTP status codes with a FastAPI `{"detail": ...}`
body.

| Status | Trigger | Body `detail` |
|---|---|---|
| 400 | Missing/empty/non-string `text` | `Provide non-empty 'text'.` |
| 400 | Missing/empty `labels`, or wrong type | `Provide non-empty 'labels'.` / `Provide 'labels' as list or dict.` |
| 400 | `labels` longer than `MAX_LABELS` | `'labels' exceeds MAX_LABELS=256.` |
| 400 | Missing/empty `schema` | `Provide non-empty 'schema' object.` |
| 400 | Missing/empty `schema_config`, or a sub-key of the wrong type | `Provide non-empty 'schema_config' object.` / `'schema_config.entities' must be a list.` |
| 413 | `text` longer than `MAX_TEXT_CHARS` | `'text' exceeds MAX_TEXT_CHARS=20000.` |
| 413 | `texts` longer than `MAX_BATCH_SIZE` | `'texts' exceeds MAX_BATCH_SIZE=64.` |
| 501 | Boundary-only endpoint called on a span model | `'extract_relations' requires a GLiNER2.5 boundary checkpoint; ...` |
| 500 | Inference raised inside the model | Exception string |
| 503 | No inference slot free within `INFERENCE_ACQUIRE_TIMEOUT_SECONDS` | `Server is busy; no inference slot available within 10.0s.` |
| 504 | Inference exceeded `REQUEST_TIMEOUT_SECONDS` | `<op_name> timed out after 120.0s.` |

Reproduce a `413`:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d "{\"text\":\"$(head -c 20001 /dev/zero | tr '\0' 'a')\",\"labels\":[\"x\"]}"
```

Reproduce a `400`:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{"labels": ["person"]}'
```

### Client guidance

- **503 is backpressure, not failure.** With `MAX_CONCURRENT_INFERENCES=1` the
  service deliberately serializes GPU work. Retry with jitter rather than
  fanning out more concurrent requests.
- **504 means the request was too big for the budget**, not that the service is
  down. Split the document and retry.
- Health checks are cheap and never queue behind inference; monitoring should
  poll `/health`, not an inference endpoint.

## Configuration that changes API behavior

These environment variables are set on the container and are visible in the
error semantics above.

| Variable | Default | Effect on the API |
|---|---|---|
| `MODEL_ID` | `fastino/gliner2.5-base-v1` | Which model answers requests; reported by `/health` |
| `MODEL_DIR` | `./models` | Where weights live inside the container |
| `MODEL_PRELOAD` | `1` | `0` defers loading to the first request, so that request is slow and `/health` reports `loaded: false` until then |
| `MAX_CONCURRENT_INFERENCES` | `1` | Semaphore width; how many requests may be in the model at once |
| `INFERENCE_ACQUIRE_TIMEOUT_SECONDS` | `10` | How long a request waits for a slot before `503` |
| `REQUEST_TIMEOUT_SECONDS` | `120` | Per-request inference budget before `504` |
| `MAX_TEXT_CHARS` | `20000` | `413` threshold |
| `MAX_LABELS` | `256` | `400` threshold for label lists |
| `MAX_SCHEMA_FIELDS` | `256` | `400` threshold for schema fields |

See [runbook.md](runbook.md) for how to change these on a running deployment.
