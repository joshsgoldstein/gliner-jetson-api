# API Reference

Endpoint reference for the GLiNER2 inference service running on `jarvita-agx`.

- **Base URL (LAN):** `http://192.168.1.177:8013`
- **Container port:** `8012` (published on host port `8013`)
- **Content type:** all `POST` endpoints take and return `application/json`

Every example below is copy-pasteable. All request/response pairs on this page
were captured from the live service on `jarvita-agx` serving
`fastino/gliner2.5-base-v1` (`architecture: boundary`). Where a response could
not be captured on this deployment — the `501` case needs a span checkpoint —
that is called out explicitly.

Interactive docs, generated by FastAPI, are served from the same base URL:

| Path | What it is |
|---|---|
| `/docs` | Swagger UI |
| `/redoc` | ReDoc |
| `/openapi.json` | Raw OpenAPI schema |

```bash
curl -s http://192.168.1.177:8013/openapi.json \
  | python3 -c "import json,sys; d=json.load(sys.stdin); [print(m.upper(), p) for p,v in d['paths'].items() for m in v]"
```

## Endpoint summary

Twelve routes. The four batch routes and `/extract_relations` require a
GLiNER2.5 **boundary** checkpoint; on a span checkpoint they return `501`.

| Method | Path | Purpose | Boundary only |
|---|---|---|---|
| GET | `/health` | Liveness, model/device state, load level | no |
| GET | `/health/deep` | Liveness **plus** a real inference probe | no |
| GET | `/version` | Library, model, and weight fingerprint | no |
| POST | `/extract_entities` | Zero-shot named entity extraction | no |
| POST | `/classify_text` | Text classification | no |
| POST | `/extract_structured` | Structured JSON extraction against a schema | no |
| POST | `/extract_multitask` | Entities + classification + relations + structure in one pass | no |
| POST | `/extract_relations` | Typed relation triples | **yes** |
| POST | `/extract_entities_batch` | Entity extraction over many documents | **yes** |
| POST | `/classify_text_batch` | Classification over many documents | **yes** |
| POST | `/extract_relations_batch` | Relation extraction over many documents | **yes** |
| POST | `/extract_multitask_batch` | One schema applied across many documents | **yes** |

## Inference options

Every `POST` extract/classify route — single and batch — accepts the same set of
optional inference parameters at the **top level** of the payload, alongside
`text`/`texts` and the task fields.

These used to be accepted and silently dropped. They are now honoured, and bad
values return `400` rather than being ignored.

| Key | Type | Default | Effect |
|---|---|---|---|
| `threshold` | number in `[0, 1]` | `0.5` | Minimum score for a prediction to be returned. Genuinely filters. Out of range → `400` |
| `include_confidence` | boolean | `false` | Return per-prediction scores; changes the response shape (below) |
| `include_spans` | boolean | `false` | Return real character offsets into the input text; changes the response shape |
| `max_len` | positive integer | model default | Chunk window for long documents |
| `overlap_policy` | string | model default | How overlapping predictions across chunks are reconciled |
| `batch_size` | positive integer | model default | **Batch routes only.** Clamped server-side to `MAX_BATCH_SIZE` (default 64) |

### `threshold`

The default `0.5` is permissive for a confident model. Verified sweep against
one sentence on the live service:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The Jaguar was spotted near the old mill road at dusk by a ranger from Devon.",
    "labels": ["company", "animal", "person", "location"],
    "threshold": 0.5
  }'
```

| `threshold` | Verified response |
|---|---|
| `0.2` | `{"entities":{"company":[],"animal":["Jaguar"],"person":["ranger"],"location":["old mill road","Devon"]}}` |
| `0.9` | `{"entities":{"company":[],"animal":["Jaguar"],"person":["ranger"],"location":["old mill road","Devon"]}}` |
| `0.98` | `{"entities":{"company":[],"animal":["Jaguar"],"person":[],"location":["old mill road"]}}` |
| `0.995` | `{"entities":{"company":[],"animal":["Jaguar"],"person":[],"location":[]}}` |
| `0.999` | `{"entities":{"company":[],"animal":[],"person":[],"location":[]}}` |

Two things follow. First, on unambiguous text this model sits above `0.99`, so
nothing between `0.2` and `0.9` changes the answer — do not expect `threshold`
to be a useful precision dial on clean input. Second, the label always survives
as a key with an empty list; filtering never drops the key.

Out-of-range and wrong-type values are rejected:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{"text": "Tim Cook.", "labels": ["person"], "threshold": 1.5}'
```

```json
{"detail": "'threshold' must be in [0, 1]."}
```

### `include_confidence` and `include_spans`

These change the **shape** of the returned entities. A client that indexes into
bare strings will break when either flag is turned on. Decide once per consumer
and stay consistent.

Baseline (neither flag):

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Apple CEO Tim Cook announced iPhone 15 in Cupertino.",
    "labels": ["company", "person", "product", "location"]
  }'
```

```json
{"entities": {"company": ["Apple"], "person": ["Tim Cook"], "product": ["iPhone 15"], "location": ["Cupertino"]}}
```

With `"include_confidence": true`:

```json
{
  "entities": {
    "company": [{"text": "Apple", "confidence": 0.9976344108581543}],
    "person": [{"text": "Tim Cook", "confidence": 0.9948838353157043}],
    "product": [{"text": "iPhone 15", "confidence": 0.9933070540428162}],
    "location": [{"text": "Cupertino", "confidence": 0.997490644454956}]
  }
}
```

With `"include_spans": true`:

```json
{
  "entities": {
    "company": [{"text": "Apple", "start": 0, "end": 5}],
    "person": [{"text": "Tim Cook", "start": 10, "end": 18}],
    "product": [{"text": "iPhone 15", "start": 29, "end": 38}],
    "location": [{"text": "Cupertino", "start": 42, "end": 51}]
  }
}
```

Offsets are real character offsets into the `text` you sent —
`text[start:end]` reproduces the span exactly. On a **batch** route the offsets
are relative to each document, not to the concatenated batch. Verified:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": [
      "Apple CEO Tim Cook announced iPhone 15 in Cupertino.",
      "Satya Nadella leads Microsoft from Redmond."
    ],
    "labels": ["company", "person"],
    "include_spans": true,
    "batch_size": 8
  }'
```

```json
{
  "results": [
    {"entities": {"company": [{"text": "Apple", "start": 0, "end": 5}], "person": [{"text": "Tim Cook", "start": 10, "end": 18}]}},
    {"entities": {"company": [{"text": "Microsoft", "start": 20, "end": 29}], "person": [{"text": "Satya Nadella", "start": 0, "end": 13}]}}
  ]
}
```

Both flags together merge into one object per prediction:

```json
{
  "entities": {
    "company": [{"text": "Apple", "confidence": 0.9976344108581543, "start": 0, "end": 5}]
  }
}
```

Classification responses change shape too. `/classify_text` normally returns a
bare label; with `"include_confidence": true` it returns an object:

```json
{"sentiment": {"label": "negative", "confidence": 0.9999998807907104}}
```

So does `/classify_text_batch`:

```json
{"results": [
  {"sentiment": {"label": "negative", "confidence": 1.0}},
  {"sentiment": {"label": "positive", "confidence": 0.9999964237213135}}
]}
```

Relations change shape most: a `[head, tail]` pair becomes a pair of objects.

```json
{
  "relation_extraction": {
    "works_for": [
      {"head": {"text": "Satya Nadella", "confidence": 0.9527838230133057},
       "tail": {"text": "Microsoft", "confidence": 0.9527838230133057}}
    ]
  }
}
```

Head and tail carry the same confidence — it is the score of the relation, not
of each argument.

### `max_len` and `overlap_policy`

Chunking controls for documents longer than the model window. `max_len` is the
window; `overlap_policy` decides how predictions from overlapping chunks are
reconciled. Both are forwarded to `gliner2` unchanged, so the accepted
`overlap_policy` values are the library's, not the API's — the API only checks
that it is a non-empty string.

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Apple CEO Tim Cook announced iPhone 15 in Cupertino. Satya Nadella leads Microsoft from Redmond.",
    "labels": ["company", "person", "location"],
    "max_len": 384,
    "overlap_policy": "longest"
  }'
```

```json
{"entities": {"company": ["Apple", "Microsoft"], "person": ["Tim Cook", "Satya Nadella"], "location": ["Redmond", "Cupertino"]}}
```

Leave both unset unless you are actually chunking. On short documents they
change nothing and only add a way to get it wrong.

### Strict payload validation

Any key that is neither a task field nor an inference option returns `400`
listing what was allowed. Previously an unrecognised key was ignored, so a typo
produced a plausible-looking result that was quietly missing whatever you
thought you had configured.

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{"text": "Tim Cook.", "labels": ["person"], "treshold": 0.5}'
```

```json
{"detail": "Unknown payload key(s): ['treshold']. Allowed: ['include_confidence', 'include_spans', 'labels', 'max_len', 'overlap_policy', 'text', 'threshold']."}
```

The same applies inside `schema_config` — see
[`/extract_multitask`](#post-extract_multitask).

## GET /health

Liveness plus model, device, and load state. Takes one optional query
parameter, `probe`.

```bash
curl -s http://192.168.1.177:8013/health
```

Verified response:

```json
{
  "status": "ok",
  "model_id": "fastino/gliner2.5-base-v1",
  "model_path": "./models/fastino/gliner2.5-base-v1",
  "loaded": true,
  "architecture": "boundary",
  "model_class": "BoundaryExtractor",
  "device": "cuda",
  "gpu": "Orin",
  "max_concurrent_inferences": 1,
  "inflight": 0,
  "saturated": false
}
```

| Field | Meaning |
|---|---|
| `status` | `"ok"`, or `"degraded"` when a probe failed (that response is served with `503`) |
| `loaded` | `false` until the model is resident. With `MODEL_PRELOAD=0` this stays `false` until the first inference request |
| `device` | `"cuda"` or `"cpu"`. `"cpu"` on a Jetson means the GPU was not visible — see the runbook |
| `gpu` | `torch.cuda.get_device_name(0)`; `"Orin"` on an AGX Orin. `null` on CPU |
| `architecture` | `"span"` for GLiNER2, `"boundary"` for GLiNER2.5. `null` before load |
| `model_class` | The loaded class, e.g. `BoundaryExtractor` for a 2.5 checkpoint, `GLiNER2` for a span one. `null` before load |
| `max_concurrent_inferences` | Current semaphore width — the live value, which may differ from the `1` default |
| `inflight` | Requests holding an inference slot right now |
| `saturated` | `inflight >= max_concurrent_inferences`. `true` means the next request queues, and will `503` if it waits longer than `INFERENCE_ACQUIRE_TIMEOUT_SECONDS` |

Without `probe`, `/health` never touches the GPU. It stays responsive while an
inference is in flight, which makes it a fine container healthcheck — but a
loaded model is not a working one, and a wedged worker will keep answering
`status: ok` here indefinitely. Use `/health/deep` for monitoring.

### `?probe=1`

Runs a real inference and reports it. **The probe deliberately bypasses the
inference semaphore**: with `MAX_CONCURRENT_INFERENCES=1`, a probe that queued
behind a hung request would hang too, making a wedged worker and a merely busy
one indistinguishable. Bypassing the semaphore keeps them distinguishable.

```bash
curl -s 'http://192.168.1.177:8013/health?probe=1'
```

Verified response (the probe text is fixed server-side by `HEALTH_PROBE_TEXT`,
against the fixed label `["company"]`):

```json
{
  "status": "ok",
  "model_id": "fastino/gliner2.5-base-v1",
  "model_path": "./models/fastino/gliner2.5-base-v1",
  "loaded": true,
  "architecture": "boundary",
  "model_class": "BoundaryExtractor",
  "device": "cuda",
  "gpu": "Orin",
  "max_concurrent_inferences": 1,
  "inflight": 0,
  "saturated": false,
  "probe": {"ok": true, "latency_ms": 109.5, "result": {"entities": {"company": ["Apple"]}}}
}
```

If the probe does not finish within `HEALTH_PROBE_TIMEOUT_SECONDS` (default 5),
or raises, the response is **`503`** with `status: "degraded"` and
`probe.ok: false`:

```json
{
  "status": "degraded",
  "probe": {"ok": false, "latency_ms": 5001.3, "error": "TimeoutError: "}
}
```

## GET /health/deep

`/health?probe=1` under a fixed path, so monitoring can be pointed at a URL with
no query string. Always probes; identical body and identical `503`-on-failure
behaviour.

**This is the endpoint monitoring should poll.** `/health` alone cannot tell you
the model still works.

```bash
curl -s http://192.168.1.177:8013/health/deep
```

Verified response:

```json
{
  "status": "ok",
  "model_id": "fastino/gliner2.5-base-v1",
  "model_path": "./models/fastino/gliner2.5-base-v1",
  "loaded": true,
  "architecture": "boundary",
  "model_class": "BoundaryExtractor",
  "device": "cuda",
  "gpu": "Orin",
  "max_concurrent_inferences": 1,
  "inflight": 0,
  "saturated": false,
  "probe": {"ok": true, "latency_ms": 125.2, "result": {"entities": {"company": ["Apple"]}}}
}
```

Scripted check:

```bash
curl -sf http://192.168.1.177:8013/health/deep >/dev/null && echo OK || echo DEGRADED
```

`curl -f` is enough — a failed probe is a `503`, so no JSON parsing is needed to
alert on it.

The semaphore bypass is what makes this useful under load. Measured on
`jarvita-agx`: while a 48-document batch held the only inference slot,
`/health/deep` returned `200` in **1.56 s** while a normal inference request on
the same box queued for **4.08 s**. Single measurement against one saturating
batch — indicative of the mechanism working, not a latency SLO.

## GET /version

Library **and** model identity. Downstream consumers stamp this onto extracted
rows, so it has to identify which weights produced a result — extractions from
two different checkpoints are otherwise indistinguishable once stored.

```bash
curl -s http://192.168.1.177:8013/version
```

Verified response:

```json
{
  "gliner2": "2.0.0",
  "model_id": "fastino/gliner2.5-base-v1",
  "model_revision": "4a3138e2432c24b4",
  "architecture": "boundary",
  "model_class": "BoundaryExtractor",
  "torch": "2.8.0"
}
```

| Field | Meaning |
|---|---|
| `gliner2` | Installed `gliner2` package version, or `"unknown"` if the distribution metadata is missing |
| `model_id` | The configured `MODEL_ID` |
| `model_revision` | 16-hex-char fingerprint of the loaded weights, for provenance stamping. Derived from `MODEL_ID` plus the size and mtime of `model.safetensors` — stable across restarts, and it changes if the weights are replaced |
| `architecture` | `"span"` or `"boundary"`; `null` before load |
| `model_class` | Loaded class name; `null` before load |
| `torch` | `torch.__version__` inside the container |

`model_revision` is a local fingerprint, not a Hugging Face commit SHA. It is
stable and comparable **within** this deployment: two rows carrying the same
revision came from the same weights file. It is not meaningful to compare across
hosts, because mtime is a local fact.

## POST /extract_entities

Zero-shot NER. You supply the label set per request; nothing is fine-tuned.

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` (default 20000) |
| `labels` | array of strings, **or** object mapping label → description | yes | Non-empty, `<= MAX_LABELS` (default 256) |
| *inference options* | — | no | See [Inference options](#inference-options) |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Patient received 400mg ibuprofen for severe headache at 2 PM.",
    "labels": ["medication", "dosage", "symptom", "time"]
  }'
```

Verified response:

```json
{
  "entities": {
    "medication": ["ibuprofen"],
    "dosage": ["400mg"],
    "symptom": ["severe headache"],
    "time": ["2 PM"]
  }
}
```

The response keys are exactly the labels you sent. A label with no match maps to
an empty list. Values are the surface spans as they appear in `text` — note
`"severe headache"`, not `"headache"`: span boundaries are the model's choice,
so do not assume they match a term list you hold downstream.

Labels can also be an object, where the value is a natural-language description
used to disambiguate the label:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Patient received 400mg ibuprofen for severe headache at 2 PM.",
    "labels": {
      "medication": "name of a drug administered to the patient",
      "dosage": "amount and unit of the drug"
    }
  }'
```

Verified response:

```json
{"entities": {"medication": ["ibuprofen"], "dosage": ["400mg"]}}
```

## POST /classify_text

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `labels` | array of strings, **or** object mapping task name → array of class labels | yes | Non-empty, `<= MAX_LABELS` entries |
| *inference options* | — | no | See [Inference options](#inference-options) |

The object form names the classification task, and the response is keyed by that
name. Prefer it, because the output key is then predictable.

```bash
curl -s -X POST http://192.168.1.177:8013/classify_text \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The battery life is terrible and it overheats constantly.",
    "labels": {"sentiment": ["positive", "negative", "neutral"]}
  }'
```

Verified response:

```json
{"sentiment": "negative"}
```

Multiple independent classification tasks can be requested in one call by adding
more keys to the `labels` object:

```bash
curl -s -X POST http://192.168.1.177:8013/classify_text \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The battery life is terrible and it overheats constantly.",
    "labels": {
      "sentiment": ["positive", "negative", "neutral"],
      "topic": ["battery", "display", "software", "build quality"]
    }
  }'
```

Verified response:

```json
{"sentiment": "negative", "topic": "battery"}
```

## POST /extract_structured

Fills a declared schema from free text. Backed by `extract_json()` in the
library.

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `schema` | object | yes | Non-empty, `<= MAX_SCHEMA_FIELDS` top-level keys |
| *inference options* | — | no | See [Inference options](#inference-options) |

Each top-level key of `schema` is a record name; its value is a list of field
specs. A field spec is a `::`-delimited string:

```
"<field_name>::<dtype>"
"<field_name>::<dtype>::<description>"
```

`dtype` is `str` or `list`. The optional third segment is a natural-language
description that steers extraction.

```bash
curl -s -X POST http://192.168.1.177:8013/extract_structured \
  -H "Content-Type: application/json" \
  -d '{
    "text": "The Sony WH-1000XM5 headphones cost $399 and ship in 3 days.",
    "schema": {
      "product": ["name::str", "price::str", "shipping::str"]
    }
  }'
```

Verified response:

```json
{"product": [{"name": "Sony WH-1000XM5", "price": "$399", "shipping": "3 days"}]}
```

The value is a **list** of records — the schema may match more than once in a
document. Index `[0]` only when you know the text holds a single record.

With descriptions:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_structured \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Goldman Sachs processed a $2.5M equity trade for Tesla Inc.",
    "schema": {
      "transaction": [
        "broker::str::Financial institution",
        "amount::str::Transaction amount",
        "security::str::Stock name"
      ]
    }
  }'
```

Verified response:

```json
{"transaction": [{"broker": "Goldman Sachs", "amount": "$2.5M", "security": "Tesla Inc."}]}
```

## POST /extract_multitask

Runs entity extraction, classification, relation extraction, and structured
extraction against one text in a single forward pass.

**Everything nests under `schema_config`.** There are no top-level `entities` /
`classification` / `relations` / `structure` keys. Sending them at the top level
returns `400` naming the offending key.

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `schema_config` | object | yes | Non-empty. All four sub-keys below are optional, but supply at least one |
| `schema_config.entities` | array of strings | no | Entity labels, `<= MAX_LABELS` |
| `schema_config.classification` | object | no | `{"name": str, "labels": [str, ...]}`, `labels` `<= MAX_LABELS` |
| `schema_config.relations` | array of strings | no | Relation type names, `<= MAX_LABELS`. **Boundary checkpoints only** |
| `schema_config.structure` | object | no | `{"name": str, "fields": [...]}`, `fields` `<= MAX_SCHEMA_FIELDS` |
| *inference options* | — | no | See [Inference options](#inference-options) |

`schema_config` accepts exactly those four keys and nothing else. Anything else
is a `400`:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_multitask \
  -H "Content-Type: application/json" \
  -d '{"text": "Tim Cook.", "schema_config": {"entitys": ["person"]}}'
```

```json
{"detail": "Unknown schema_config key(s): ['entitys']. Allowed: ['classification', 'entities', 'relations', 'structure']."}
```

Each entry of `structure.fields` is an object:

| Key | Type | Default | Notes |
|---|---|---|---|
| `name` | string | — | Field name |
| `dtype` | string | `"str"` | `"str"` or `"list"` |
| `description` | string | `null` | Optional steering text |
| `choices` | array | `null` | Optional closed vocabulary for the field |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_multitask \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Apple CEO Tim Cook announced record revenue in Cupertino.",
    "schema_config": {
      "entities": ["company", "person", "location"],
      "classification": {"name": "sentiment", "labels": ["positive", "negative"]},
      "structure": {
        "name": "announcement",
        "fields": [
          {"name": "who", "dtype": "str"},
          {"name": "what", "dtype": "str"}
        ]
      }
    }
  }'
```

Verified response:

```json
{
  "announcement": [{"who": "Tim Cook", "what": "record revenue"}],
  "entities": {
    "company": ["Apple"],
    "person": ["Tim Cook"],
    "location": ["Cupertino"]
  },
  "sentiment": "positive"
}
```

The response is a flat object. Entities land under `entities`; the
classification lands under the `name` you gave it (`sentiment`); the structure
lands under its `name` (`announcement`) as a list of records; relations land
under `relation_extraction`. Key ordering is not guaranteed — address the
response by key.

### `relations` inside `schema_config`

`schema_config.relations` was previously accepted and silently dropped, so a
request asking for relations came back looking successful with no relations in
it. It is now honoured, and requires a boundary checkpoint like the dedicated
route does.

```bash
curl -s -X POST http://192.168.1.177:8013/extract_multitask \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Satya Nadella, CEO of Microsoft, met Sam Altman of OpenAI in Seattle.",
    "schema_config": {
      "entities": ["company", "person"],
      "relations": ["works_for", "met_with"]
    }
  }'
```

Verified response:

```json
{
  "entities": {
    "company": ["Microsoft", "OpenAI"],
    "person": ["Satya Nadella", "Sam Altman"]
  },
  "relation_extraction": {
    "works_for": [["Satya Nadella", "Microsoft"]],
    "met_with": [["Satya Nadella", "Sam Altman"]]
  }
}
```

Entities and relations from one forward pass, rather than two round trips.

## POST /extract_relations

Extract typed relation triples. **Requires a GLiNER2.5 boundary checkpoint** —
on a span model this returns `501`.

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | Non-empty, `<= MAX_TEXT_CHARS` |
| `relations` | array of strings, **or** object mapping relation → description | yes | Relation type names; `<= MAX_LABELS` |
| *inference options* | — | no | See [Inference options](#inference-options) |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_relations \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Satya Nadella, CEO of Microsoft, met Sam Altman of OpenAI in Seattle.",
    "relations": ["works_for", "met_with", "located_in"]
  }'
```

Verified response:

```json
{
  "relation_extraction": {
    "works_for": [["Satya Nadella", "Microsoft"]],
    "met_with": [["Satya Nadella", "Sam Altman"]],
    "located_in": [["Sam Altman", "Seattle"]]
  }
}
```

Each relation name maps to a list of `[head, tail]` pairs. The model extracts
what the sentence supports and applies no type constraint you did not give it —
`located_in` here returned a person, not the organization you might have
expected. Validate argument types downstream if you need them.

With `"include_confidence": true` the pairs become objects — see
[Inference options](#include_confidence-and-include_spans).

On a span checkpoint (not reproducible on this deployment, which serves a
boundary model; message assembled by `_require_boundary` in `app.py`):

```json
{"detail": "'extract_relations' requires a GLiNER2.5 boundary checkpoint; loaded model 'fastino/gliner2-large-v1' has architecture 'span'. Set MODEL_ID to e.g. fastino/gliner2.5-multi-v1."}
```

## Batch endpoints

Four routes take a `texts` list instead of a `text` string. All four:

- require a **boundary** checkpoint (`501` otherwise);
- return `{"results": [...]}` **positionally aligned** with the `texts` sent;
- hold **one** inference slot for the whole batch, rather than contending for
  the semaphore once per document;
- accept every [inference option](#inference-options) plus `batch_size`;
- are bounded by both `MAX_BATCH_SIZE` (default 64 documents) and
  `MAX_BATCH_CHARS` (default 200000 characters summed across the batch) —
  either overrun is a `413`.

`MAX_BATCH_CHARS` exists because `MAX_BATCH_SIZE` alone does not bound memory:
64 documents of `MAX_TEXT_CHARS` each is what OOMs the box.

### POST /extract_entities_batch

| Field | Type | Notes |
|---|---|---|
| `texts` | array of strings | `<= MAX_BATCH_SIZE`; each element `<= MAX_TEXT_CHARS`; sum `<= MAX_BATCH_CHARS` |
| `labels` | array or object | Same shape as `/extract_entities`; applied to every document |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": [
      "Apple CEO Tim Cook announced iPhone 15 in Cupertino.",
      "Satya Nadella leads Microsoft from Redmond."
    ],
    "labels": ["company", "person", "location"]
  }'
```

Verified response:

```json
{
  "results": [
    {"entities": {"company": ["Apple"], "person": ["Tim Cook"], "location": ["Cupertino"]}},
    {"entities": {"company": ["Microsoft"], "person": ["Satya Nadella"], "location": ["Redmond"]}}
  ]
}
```

### POST /classify_text_batch

| Field | Type | Notes |
|---|---|---|
| `texts` | array of strings | As above |
| `labels` | array or object | Same shape as `/classify_text`; applied to every document |

```bash
curl -s -X POST http://192.168.1.177:8013/classify_text_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": ["The battery is terrible.", "Works flawlessly, love it."],
    "labels": {"sentiment": ["positive", "negative", "neutral"]}
  }'
```

Verified response:

```json
{"results": [{"sentiment": "negative"}, {"sentiment": "positive"}]}
```

### POST /extract_relations_batch

| Field | Type | Notes |
|---|---|---|
| `texts` | array of strings | As above |
| `relations` | array or object | Relation type names; applied to every document |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_relations_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": [
      "Satya Nadella, CEO of Microsoft, met Sam Altman of OpenAI.",
      "Tim Cook runs Apple from Cupertino."
    ],
    "relations": ["works_for", "met_with"]
  }'
```

Verified response:

```json
{
  "results": [
    {"relation_extraction": {"works_for": [["Satya Nadella", "Microsoft"]], "met_with": [["Satya Nadella", "Sam Altman"]]}},
    {"relation_extraction": {"works_for": [["Tim Cook", "Cupertino"]], "met_with": []}}
  ]
}
```

The second result is worth reading closely: `works_for` returned
`["Tim Cook", "Cupertino"]` — a place, not the company in the same sentence.
Relation output needs downstream validation; it is not type-checked for you.

### POST /extract_multitask_batch

One schema applied across many documents. This is the highest-throughput route
in the service.

| Field | Type | Notes |
|---|---|---|
| `texts` | array of strings | As above |
| `schema_config` | object | Identical shape and validation to `/extract_multitask` |

```bash
curl -s -X POST http://192.168.1.177:8013/extract_multitask_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": [
      "Apple CEO Tim Cook announced record revenue in Cupertino.",
      "Satya Nadella leads Microsoft from Redmond."
    ],
    "schema_config": {
      "entities": ["company", "person"],
      "classification": {"name": "sentiment", "labels": ["positive", "negative"]}
    }
  }'
```

Verified response:

```json
{
  "results": [
    {"entities": {"company": ["Apple"], "person": ["Tim Cook"]}, "sentiment": "positive"},
    {"entities": {"company": ["Microsoft"], "person": ["Satya Nadella"]}, "sentiment": "positive"}
  ]
}
```

With `relations` in the schema:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_multitask_batch \
  -H "Content-Type: application/json" \
  -d '{
    "texts": [
      "Satya Nadella, CEO of Microsoft, met Sam Altman of OpenAI in Seattle.",
      "Tim Cook runs Apple from Cupertino."
    ],
    "schema_config": {
      "entities": ["company", "person"],
      "relations": ["works_for"]
    }
  }'
```

Verified response:

```json
{
  "results": [
    {"entities": {"company": ["Microsoft", "OpenAI"], "person": ["Satya Nadella", "Sam Altman"]},
     "relation_extraction": {"works_for": [["Satya Nadella", "Microsoft"], ["Sam Altman", "OpenAI"]]}},
    {"entities": {"company": ["Cupertino", "Apple"], "person": ["Tim Cook"]},
     "relation_extraction": {"works_for": [["Tim Cook", "Cupertino"]]}}
  ]
}
```

### Throughput: use one multitask batch, not three batch calls

Measured on `jarvita-agx` over 32 documents against
`fastino/gliner2.5-base-v1`:

| Approach | Per document | Documents/min |
|---|---|---|
| 3 sequential single calls per document (entities, classification, structure) | 274.9 ms | 218 |
| 1 `/extract_multitask_batch` call | 25.8 ms | 2326 |

**10.7x.** Measured on a shared box in one run over 32 documents — indicative of
the right order of magnitude, not a controlled benchmark.

The win has two sources, worth separating: batching amortizes per-call overhead
across documents, and multitask does entities + classification + structure in
one forward pass rather than three. Calling `/extract_entities_batch`,
`/classify_text_batch` and `/extract_structured` separately gets you the first
but not the second.

**Schema caching between batch calls buys nothing.** Measured over 16 documents:
127.41 ms with a reused schema versus 127.42 ms rebuilding it — a 0.01 ms
difference, which is noise. Do not build caching for it.

## Errors

The service returns standard HTTP status codes with a FastAPI `{"detail": ...}`
body.

| Status | Trigger | Body `detail` (verified unless noted) |
|---|---|---|
| 400 | Unknown key in the payload | `Unknown payload key(s): ['treshold']. Allowed: ['include_confidence', 'include_spans', 'labels', 'max_len', 'overlap_policy', 'text', 'threshold'].` |
| 400 | Unknown key in `schema_config` | `Unknown schema_config key(s): ['entitys']. Allowed: ['classification', 'entities', 'relations', 'structure'].` |
| 400 | Task field at the top level instead of in `schema_config` | `Unknown payload key(s): ['entities']. Allowed: [...]` |
| 400 | Missing/empty/non-string `text` | `Provide non-empty 'text'.` |
| 400 | Missing/empty `texts` on a batch route | `Provide non-empty 'texts' list.` |
| 400 | Missing/empty `labels`, or wrong type | `Provide non-empty 'labels'.` / `Provide 'labels' as list or dict.` |
| 400 | `labels` longer than `MAX_LABELS` | `'labels' exceeds MAX_LABELS=256.` |
| 400 | Missing/empty `schema` | `Provide non-empty 'schema' object.` |
| 400 | Missing/empty `schema_config`, or a sub-key of the wrong type | `Provide non-empty 'schema_config' object.` / `'schema_config.entities' must be a list.` |
| 400 | `threshold` outside `[0, 1]` | `'threshold' must be in [0, 1].` |
| 400 | `threshold` not a number | `'threshold' must be a number in [0, 1].` |
| 400 | `include_confidence` / `include_spans` not a boolean | `'include_spans' must be a boolean.` |
| 400 | `max_len` not a positive integer | `'max_len' must be a positive integer.` |
| 400 | `overlap_policy` not a non-empty string | `'overlap_policy' must be a non-empty string.` |
| 400 | `batch_size` not a positive integer | `'batch_size' must be a positive integer.` |
| 413 | `text` longer than `MAX_TEXT_CHARS` | `'text' exceeds MAX_TEXT_CHARS=20000.` |
| 413 | `texts` longer than `MAX_BATCH_SIZE` | `'texts' exceeds MAX_BATCH_SIZE=64.` |
| 413 | Batch character total over `MAX_BATCH_CHARS` | `batch totals 285000 chars, exceeding MAX_BATCH_CHARS=200000. Split the batch.` |
| 501 | Boundary-only route called on a span model *(not reproducible on this deployment)* | `'extract_relations' requires a GLiNER2.5 boundary checkpoint; loaded model '...' has architecture 'span'. Set MODEL_ID to e.g. fastino/gliner2.5-multi-v1.` |
| 500 | Inference raised inside the model | Exception string |
| 503 | No inference slot free within `INFERENCE_ACQUIRE_TIMEOUT_SECONDS` | `Server is busy; no inference slot available within 10.0s.` |
| 503 | `/health?probe=1` or `/health/deep` probe failed or timed out | Full health body with `status: "degraded"` and `probe.ok: false` |
| 504 | Inference exceeded `REQUEST_TIMEOUT_SECONDS` | `<op_name> timed out after 120.0s.` |

Note the split between `400` and `413` on size: label and schema-field counts
are `400`; anything measured in characters or documents is `413`.

Reproduce a `413` on `text`:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d "{\"text\":\"$(head -c 20001 /dev/zero | tr '\0' 'a')\",\"labels\":[\"x\"]}"
```

```json
{"detail": "'text' exceeds MAX_TEXT_CHARS=20000."}
```

Reproduce a `413` on batch characters — 15 documents, each well under
`MAX_TEXT_CHARS`, and 15 is well under `MAX_BATCH_SIZE`, and it is still
rejected:

```bash
python3 -c "import json; print(json.dumps({'texts': ['a'*19000]*15, 'labels': ['person']}))" \
  | curl -s -X POST http://192.168.1.177:8013/extract_entities_batch \
      -H "Content-Type: application/json" --data @-
```

```json
{"detail": "batch totals 285000 chars, exceeding MAX_BATCH_CHARS=200000. Split the batch."}
```

Every limit named in a `413`/`400` detail is the **live configured value**, not
the code default — the deployment may run tighter. Clients that chunk should
read the number out of the detail rather than hardcoding it, or discover it once
at startup with a deliberate overrun.

Reproduce a `400`:

```bash
curl -s -X POST http://192.168.1.177:8013/extract_entities \
  -H "Content-Type: application/json" \
  -d '{"labels": ["person"]}'
```

```json
{"detail": "Provide non-empty 'text'."}
```

### Client guidance

- **A `400` on a key you thought was fine is the strict validation, not a
  regression.** Read the `Allowed:` list in the detail; it is generated from the
  route's own key set.
- **503 is backpressure, not failure.** With `MAX_CONCURRENT_INFERENCES=1` the
  service deliberately serializes GPU work. Retry with jitter rather than
  fanning out more concurrent requests. Better: batch.
- **504 means the request was too big for the budget**, not that the service is
  down. Split the document and retry.
- **413 on a batch is a client-side split, not a config change.** Chunk against
  both bounds — document count and total characters.
- **Monitoring should poll `/health/deep`**, which proves the model still runs a
  forward pass. `/health` alone reports `ok` for a wedged worker.
- **Pin your response-shape expectations to your flags.** `include_confidence`
  and `include_spans` are per-request, so one client turning them on does not
  affect another — but a client that flips them mid-stream will produce two
  incompatible shapes in the same dataset.

## Configuration that changes API behavior

These environment variables are set on the container and are visible in the
error semantics above.

| Variable | Default | Effect on the API |
|---|---|---|
| `MODEL_ID` | `fastino/gliner2.5-base-v1` | Which model answers requests; reported by `/health` and `/version`. A span checkpoint makes the five boundary-only routes return `501` |
| `MODEL_DIR` | `./models` | Where weights live inside the container |
| `MODEL_PRELOAD` | `1` | `0` defers loading to the first request, so that request is slow and `/health` reports `loaded: false` until then |
| `MAX_CONCURRENT_INFERENCES` | `1` | Semaphore width; how many requests may be in the model at once. Reported by `/health`, and the denominator of `saturated` |
| `INFERENCE_ACQUIRE_TIMEOUT_SECONDS` | `10` | How long a request waits for a slot before `503` |
| `REQUEST_TIMEOUT_SECONDS` | `120` | Per-request inference budget before `504` |
| `MAX_TEXT_CHARS` | `20000` | `413` threshold per document |
| `MAX_LABELS` | `256` | `400` threshold for label, relation, and class lists |
| `MAX_SCHEMA_FIELDS` | `256` | `400` threshold for schema fields |
| `MAX_BATCH_SIZE` | `64` | `413` threshold for `texts` length; also the ceiling `batch_size` is clamped to |
| `MAX_BATCH_CHARS` | `200000` | `413` threshold for characters summed across a batch |
| `HEALTH_PROBE_TIMEOUT_SECONDS` | `5` | Probe budget before `/health/deep` returns `503 degraded` |
| `HEALTH_PROBE_TEXT` | `Apple is based in Cupertino.` | The text the probe runs against, with the fixed label `["company"]` |

See [runbook.md](runbook.md) for how to change these on a running deployment.
